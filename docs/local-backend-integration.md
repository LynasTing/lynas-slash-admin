# 本地后端联调说明

## 当前环境

- 本机通过 IntelliJ IDEA 运行 Java 后端项目
- 后端服务暂定地址为 `http://localhost:1982`
- 接口文档暂定地址为 `http://localhost:1982/swagger-ui/index.html`
- 前端开发服务默认地址为 `http://localhost:5678`

## 本地服务连通性检查

- 在沙箱内访问 `localhost:1982` 失败时，不得直接判断后端服务未启动；沙箱网络隔离可能阻止访问宿主机上的本地服务
- 应先记录沙箱内的实际错误，再申请更高权限重试健康检查、Swagger 或目标接口
- 只有沙箱内和更高权限检查均失败，或得到明确的连接拒绝、服务进程不存在等证据时，才能判断后端当前不可访问
- 更高权限检查仅用于读取本地服务状态和接口响应，不得借此修改后端数据或配置；写操作联调必须在获得明确授权后执行
- 每次联调记录实际检查地址、请求方法、响应状态、响应体摘要和失败层级（沙箱、权限、服务、认证、CORS 或接口业务错误）

## 接口契约原则

- 前端接口路径、请求方法、请求参数、响应 VO、DTO 和字段数据类型必须以后端已完成模块的接口定义为准
- 对需要由前端按当前语言展示的业务文案（例如菜单名称、导航分组名称、权限名称），接口契约必须提供稳定的 `i18nKey` 字段，而不是仅持久化某一种语言的展示文本；前端使用该键调用国际化资源。只有用户可自由输入、无法预置翻译的业务内容，才直接传输和展示文本值
- 不要根据页面展示需要擅自调整字段名、可空性、分页结构、日期格式或状态值；需要转换时，在服务层或页面边界显式处理
- 后端接口文档、实际响应和代码定义不一致时，先确认后端最终契约，再修改前端；不要让前端 mock 成为事实来源
- 新增或修改接口前，先在 Swagger 中确认请求与响应示例；文档无法覆盖的业务规则，需以服务端实现或明确约定为准
- 前端请求类型、表单校验和字段注释必须反映后端 DTO 的客户端可见约束，包括必填性、数据类型、长度、数值范围、格式和可选值；例如后端 `@Size(max = 500)` 与 Swagger 的 HTTP/HTTPS URL 约束，应分别落实为最大长度校验和 URL 格式校验，并在请求字段注释中说明
- 新增、修改表单的字段展示、必填性和校验必须同时依据接口契约与所属模块的业务语义判断；DTO 中的可选字段不代表其在所有表单场景都可不填。前端应根据当前表单内容与业务条件动态处理字段的展示、校验、默认值和提交值，避免提交不适用或残留的数据。字段的适用性、必填性或交互规则无法从后端契约、既有需求或页面上下文明确确认时，必须先向开发者确认，不得自行猜测
- 统一请求工具已负责解析接口错误并展示错误提示时，页面、组件和服务调用方的 `catch` 不得再次调用 `toast.error` 或展示同类全局错误通知，避免同一失败重复提示。调用方只处理本地恢复动作，例如结束 loading、保留表单输入或关闭局部状态；确需不同错误呈现时，应先扩展统一请求工具的职责或明确调用约定
- 不要机械复制全部后端校验注解：由字段类型、`as const` 常量集合或推导联合类型已经表达的值域，只保留一次集中定义，字段注释不再重复；仅记录 TypeScript 无法表达且会影响前端输入、展示、序列化或调用方式的约束。服务端仍是最终校验方

## Mock 数据迁移

- 项目现有 MSW mock 数据只用于本地演示，字段和数据格式可能与后端不同
- 当对应后端模块已完成时，前端应切换到真实接口，并同步调整类型、服务层和页面的数据转换
- 未完成的后端模块可以继续使用 mock，但应明确该模块尚未联调，避免将 mock 行为当成正式接口行为
- 删除或替换 mock 前，确认前端启动配置不会继续拦截目标请求

## 联调检查清单

- 确认前端 API 基地址指向本地后端，且未被开发代理或 mock worker 重写
- 确认后端已放行前端开发地址的 CORS 请求，或前端已配置等效的开发代理
- 根据后端约定校验认证请求头、Token 刷新和未授权响应处理；当前示例鉴权逻辑不能视为正式实现
- 校验统一响应结构、业务错误码、HTTP 状态码、分页字段、时间时区与格式、空值表达方式和文件上传格式
- 对创建、更新、删除等写操作，以后端返回结果重新加载页面数据，避免本地状态与服务端最终数据分叉
- 遇到联调问题时，记录请求地址、方法、请求体、响应状态和响应体，并先判断问题属于前端、后端、CORS、认证还是 mock 拦截

## 协作约定

- 前后端由同一人维护时，仍将 Swagger 和后端代码视为接口契约来源，前端类型随契约同步更新
- 接口契约发生破坏性变更时，同时更新后端文档、前端服务层、类型定义和受影响页面
- 本文件是本机环境说明，已加入 `.gitignore`，不应作为团队共享配置或生产环境配置使用

## commit 要求

本轮提交结果、剩余范围和验证证据见 `ai/current-worktree-commit-plan.md`；规则更新和验证日志不纳入业务提交。

### 提交边界

- 固定顺序为公共运行基线 → 角色模块 → 用户模块；执行前同时核对两个仓库的 HEAD、提交历史、暂存区和工作区，已完成的组记录配对 SHA，不重复提交，也不自动把本次范围顺延到下一组
- 若已提交基线阻塞全量门禁，先对照基线确认失败清单；本轮已获得单独修复格式基线的授权，在公共基线之后、角色组之前增加前后端格式维护组，角色组继续排除无关格式变更
- 前后端同时提交是指同一个业务组在两个独立 Git 仓库各自提交相关代码，不存在跨仓库的原子 Git commit
- 单组按最小可运行的业务闭环划分，不能仅依据目录划分；确有编译或运行依赖时，允许加入已核实的最小关联代码，并在计划中列出原因、文件和后续归属
- 本轮角色组允许纳入 SysUserRoleEntity 与 SysUserRoleMapper，用于删除前检查用户关联；不纳入用户 CRUD
- 共享文件按改动块拆分，只纳入本组实际使用的内容；禁止 git add . 或 git add -A
- SQL、Flyway、迁移测试及专用依赖/配置、无关 README、忽略规则、历史格式修改和本地计划文档不得混入本次业务提交；已跟踪文件不会因为写入 .gitignore 自动排除
- 单方无新增改动时记录其已有兼容提交，不制造空提交；不自动授权合并、推送或移除文件跟踪

### 提交前验证

- 验证对象必须是“该仓库已提交基线 + 本组改动”的独立快照，不能使用尚未提交的下一组代码、Flyway 或配置作为隐含依赖
- 检查日志保存在项目内 `ai/artifacts/<task>/`，通过本地 `.git/info/exclude` 排除，不混入业务提交；隔离工作区可放在项目外
- 优先在隔离工作区准备和提交；前端 lint-staged 会自动修复暂存文件，后端 pre-commit 当前会执行全项目 spotless:apply，必须防止钩子改写原工作区的无关文件
- 检查项目实际提交钩子和 Commitlint 配置；提交说明分别遵守各仓库规则，当前前端采用英文标题与中英双语正文，后端采用中文标题说明和正文
- 前端执行 pnpm format:check、pnpm lint、pnpm typecheck；角色接口迁移涉及页面与服务整合，本轮同时执行 pnpm build 验证生产产物
- 后端执行 ./mvnw verify，核对测试报告与打包产物；verify 成功且已覆盖 package 时，不对同一快照重复执行 package
- 确认数据库已具备需要的表、列和约束，不执行本轮排除的 SQL/Flyway；Swagger、后端代码和实际响应共同作为契约证据
- 在隔离工作区模拟合入主分支后验证启动、运行和打包，不修改真实主分支；本地主分支的验证不能表述为远端最新状态已经验证
- 真实接口联调使用 VITE_APP_USE_MOCK=false，同时检查 API 基地址、代理、旧 Service Worker、认证、CORS、请求和响应；写操作必须遵守本次明确授权的数据边界
- 本轮已授权在现有开发库创建唯一标识的测试角色并清理，仅操作本轮测试数据，不修改已有业务记录
- 任一格式、契约、测试、运行或打包门禁失败，停止本组提交；将失败与已提交基线比较，区分历史问题与本组新增问题。历史问题仍是全量门禁失败，不能以历史原因跳过检查或混入无关修复

### 配对提交与失败处理

1. 两个仓库的独立快照全部通过检查后，按本组清单显式暂存
2. 核对 git diff --cached --name-status、完整 staged diff 和 git diff --cached --check，确认没有无关文件及改动块
3. 根据最新暂存内容生成各自的提交信息，先提交后端，再提交前端
4. 钩子自动修复改变了已验证内容时，重新审查并补跑受影响检查，不把修复前的结果当成最终提交的证据
5. 提交完成后核对实际提交的文件清单及差异，记录双仓库 SHA；第二个仓库提交失败时，保留第一个仓库提交并记录待配对状态，修复后补齐，不重写历史或进入下一组
6. 失败时只撤销本轮产生的暂存，保留用户原有暂存及工作区内容；禁止为清理现场覆盖或删除用户改动
7. 将已验证提交同步回原分支前再次检查 HEAD 和工作区是否变化；保留全部剩余改动，不用 reset --hard 或整体覆盖方式同步
8. 更新本地计划中的提交记录、验证证据、失败项及剩余改动，按联调清单复检已提交功能；未经本轮范围授权，不继续提交后续业务组
